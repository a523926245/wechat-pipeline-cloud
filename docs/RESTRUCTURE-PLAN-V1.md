# 微信公众号 AI 自动创作系统——整体重构实施方案

**文档版本：V1.0**

**项目目标：将现有微信公众号自动创作系统重构为一套具备自主选题、内容策划、事实核验、文章创作、质量审核和持续优化能力的 AI 内容生产系统。**

---

# 一、项目背景与重构目标

## 1.1 项目背景

当前项目已经具备微信公众号自动创作的基本能力，但在实际使用和选题样本检查过程中，发现了一些系统性问题：

1. 选题生成质量不稳定，容易产生大量价值不高的选题。
2. 不同赛道的选题容易出现内容套路重复、主题趋同的问题。
3. 选题生成过度依赖固定种子和场景，缺乏真正的自主策划能力。
4. 选题去重主要依赖文本相似度，难以识别语义相同、核心问题相同的选题。
5. 赛道定位、文章结构、写作风格、选题规则散落在不同 Prompt 和配置中，容易产生规则冲突。
6. 文章结构容易模板化，不同赛道、不同文章类型缺少足够的差异。
7. AI 可能生成未经核实的数据、案例、研究结论、人物故事和引用。
8. 缺乏完整的 AI 运行记录，难以追踪某个选题或文章为什么会生成成当前的结果。
9. 缺乏系统化的质量评估、审核和持续优化机制。

本次重构不是简单修复上述问题，而是重新梳理整个内容生产系统的架构、数据模型和业务流程。

## 1.2 最终产品定位

将系统升级为：

**AI 驱动的多赛道微信公众号内容生产与质量管理系统。**

系统应当具备以下核心能力：

- 根据不同赛道自主策划有价值的选题。
- 自动判断选题是否符合赛道定位。
- 识别历史选题中的文本重复、语义重复和内容方向重复。
- 根据选题自动规划文章内容和结构。
- 根据文章实际需要决定是否进行事实核验。
- 使用真实、可追溯的来源支撑事实性内容。
- 根据赛道配置和文章类型生成不同风格、不同结构的文章。
- 对生成的文章进行系统化质量审核。
- 完整记录 AI 的输入、输出、配置和审核结果。
- 通过历史数据和质量评估持续改善生成效果。

## 1.3 核心内容原则

整个系统必须遵守以下创作原则：

**正向价值：**

内容应该有温度、有帮助、有启发，避免空洞鸡汤、制造焦虑、贩卖恐惧和刻意制造冲突。

正能量不等于回避现实问题。可以讨论困难、矛盾和压力，但应当提供理解、知识、建设性思考或实际帮助。

**真实可信：**

不得编造事实、数据、研究、人物、案例、名言、新闻或来源。

AI 的内部知识可以用于一般知识解释、观点分析和创意策划，但不能被当作已经完成外部事实核验。

**原创与多样性：**

不能仅通过替换人物、场景、身份或少量词语生成所谓的新选题。

不同赛道要有自己的内容定位，不同文章也要有合理的结构和表达差异。

**读者价值：**

每个选题都应当明确回答一个问题：

读者为什么值得花时间阅读这篇文章？

# 二、重构总体架构

将现有系统的业务流程重新规划为以下八个环节：

1. 赛道配置中心
2. 智能选题引擎
3. 选题质量审核
4. 单篇文章策划
5. 按需事实核验
6. 文章生成引擎
7. 文章质量审核
8. 发布与效果分析

整体流程：

```text
赛道配置中心
      |
      v
智能选题引擎
      |
      v
候选选题库
      |
      v
选题质量审核
      |
      +------ 不合格 ------> 拒绝 / 修改
      |
      v
正式选题库
      |
      v
单篇文章策划
      |
      v
事实需求识别
      |
      +------ 不需要外部事实
      |               |
      |               v
      |           直接创作
      |
      +------ 需要外部事实
                      |
                      v
                按需获取公开来源
                      |
                      v
                   事实核验
                      |
                      v
                  文章生成
                      |
                      v
                  文章审核
                      |
            +---------+---------+
            |                   |
          不合格              合格
            |                   |
        定向修改             待发布
                                |
                                v
                           人工确认
                                |
                                v
                            微信发布
                                |
                                v
                            效果分析
```

要求：

- 各环节职责清晰。
- 不要将所有功能塞进一个大型 Service。
- 不要为了架构复杂而拆分大量微服务。
- 第一阶段继续采用模块化单体架构即可。
- 保持现有技术栈，除非经过分析确认确实需要更换。

# 三、建立统一的赛道配置中心

这是本次重构的基础，必须优先实施。

## 3.1 当前问题

目前赛道规则、选题规则、文章结构、写作风格和 Prompt 可能分别存在于多个文件中。

这容易导致：

- 不同模块使用不同的赛道规则。
- 选题要求与文章写作要求冲突。
- 通用文章结构覆盖赛道专属要求。
- 修改一个配置，需要同步修改多个 Prompt。
- 无法准确判断模型为什么生成某种文章。

## 3.2 建立 TrackContract

为每条赛道建立一份完整、可版本化的创作契约。

建议包含：

```typescript
interface TrackContract {
  trackCode: string;
  name: string;
  version: string;

  positioning: string;

  audience: {
    description: string;
    needs: string[];
    knowledgeLevel?: string;
  };

  contentPrinciples: {
    coreValues: string[];
    preferredDirections: string[];
    forbiddenDirections: string[];
    boundaries: string[];
  };

  topicPolicy: {
    preferredTopics: string[];
    avoidTopics: string[];
    diversityRequirements: string[];
  };

  articleShape: {
    allowedTypes: string[];
    structurePolicy: string;
    paragraphPolicy: string;
    lengthPolicy?: string;
  };

  writingStyle: {
    voice: string;
    tone: string[];
    expressionRules: string[];
    forbiddenExpressions: string[];
  };

  reviewPolicy: {
    qualityRequirements: string[];
    factCheckRules: string[];
    specialRisks: string[];
  };
}
```

上述是目标接口示例，实际字段应根据现有项目的数据模型调整。

## 3.3 配置分层

赛道配置采用四层结构：

第一层：全局创作原则

- 正向价值。
- 真实可信。
- 原创性。
- 内容安全。
- 版权要求。

第二层：赛道定位

- 目标读者。
- 读者需求。
- 内容范围。
- 内容边界。
- 赛道特色。

第三层：文章形态契约

- 支持的文章类型。
- 结构组织策略。
- 篇幅策略。
- 段落组织要求。
- 文章类型与选题的匹配规则。

第四层：表达风格

- 语言风格。
- 语气。
- 表达方式。
- 禁止使用的表达。
- 赛道专属风格。

## 3.4 必须遵守的规则

所有 AI 任务都必须通过统一的配置读取和 Prompt 渲染入口获取赛道规则。

禁止在选题生成、文章生成、文章审核等服务中各自硬编码一套赛道定位。

Prompt 由配置动态生成，不再独立维护多份互相冲突的赛道规则。

每次生成必须记录实际使用的 TrackContract 版本。

## 3.5 不同赛道必须具有真实差异

例如：

| 赛道 | 内容定位 | 适合的内容形式 |
|---|---|---|
| 星座 | 趣味观察、自我探索、轻松文化话题 | 趣味观察、关系讨论、文化解读 |
| 育儿 | 儿童成长、亲子关系、家庭教育 | 知识解释、陪伴建议、经验分享 |
| 职场 | 职业成长、专业能力、工作方法 | 观点分析、经验分享、方法指南 |
| 技术 | 技术知识、工程实践、技术趋势 | 技术解读、实践经验、问题分析 |
| 教育 | 学习成长、教育观察、学习方法 | 知识科普、方法指南、教育观察 |

以上仅为定位参考，不是固定题材配额。

不能要求所有赛道都使用相同的内容类型、文章结构和表达风格。

# 四、重构智能选题引擎

这是本次重构的重点模块之一。

## 4.1 取消固定种子驱动的选题模式

检查现有 topic_seeds.json 及相关选题种子逻辑。

不要再让大量固定场景和预设问题主导选题生成。

允许保留少量经过审核的方向性参考，但不能让种子成为选题的主要来源。

新选题应主要根据以下信息自主策划：

- 赛道定位。
- 目标读者需求。
- 全局创作原则。
- 历史选题及使用情况。
- 已有选题的主题分布。
- 历史内容方向重复情况。
- 当前任务的创意要求。

AI 应自主提出新角度，而不是不断改写已有选题。

## 4.2 选题生成与审核必须分离

不能让选题生成服务直接将模型返回的结果写入正式题库。

新流程：

```text
生成候选选题
      |
      v
格式与字段校验
      |
      v
赛道匹配审核
      |
      v
质量审核
      |
      v
重复度审核
      |
      v
风险审核
      |
      v
综合判定
      |
      +---- approved
      |
      +---- needs_revision
      |
      +---- rejected
```

只有审核通过的选题才允许进入正式题库。

## 4.3 选题数据结构

建议建立 TopicCandidate：

```typescript
interface TopicCandidate {
  id: string;
  trackId: number;

  title: string;
  theme: string;
  content: string;

  contentType: string;
  coreAngle: string;
  readerValue: string;
  creativeDifference: string;

  factRequirements: string[];
  riskNotes: string[];

  qualityScore?: number;

  reviewStatus:
    | 'candidate'
    | 'reviewing'
    | 'approved'
    | 'needs_revision'
    | 'rejected';

  reviewResult?: unknown;

  createdAt: Date;
  updatedAt: Date;
}
```

实际实现应沿用项目统一的命名、ID 和时间字段规范。

候选选题与正式选题应明确区分，不能通过一个 used 布尔字段同时承担候选、审核、入库和使用状态。

## 4.4 建立选题质量评价机制

每个选题从六个维度进行 0–5 分评价：

| 评价维度 | 评价内容 |
|---|---|
| 正向价值 | 是否有帮助、有启发、有温度 |
| 赛道匹配 | 是否符合赛道定位和目标读者 |
| 读者价值 | 是否值得读者花时间阅读 |
| 具体程度 | 是否有清晰的内容切入点 |
| 创意差异 | 是否与历史内容存在明显差异 |
| 可创作性 | 是否有足够内容支撑完整文章 |

质量评分只用于辅助判断，不能通过总分掩盖严重风险。

以下情况应作为硬性审核条件：

- 虚构事实。
- 伪科学结论。
- 明显刻板偏见。
- 恐吓、羞辱和恶意对立。
- 无依据的因果结论。
- 明显偏离赛道定位。
- 无法提供实际阅读价值。

严重风险不能通过其他维度的高分抵消。

审核结果必须包含具体理由，不能只返回分数。

## 4.5 建立三层去重机制

第一层：文本去重

- 标题归一化。
- 文本相似度。
- 包含率。
- 中文字符相似度。
- 关键词和主题重叠。

第二层：语义去重

识别标题不同但表达相同问题的选题。

优先采用可替换的 Embedding 接口。

如果现有模型服务支持 Embedding，可复用现有服务；否则先实现可用的文本相似度方案，不要因为缺少向量服务而阻断整个项目。

第三层：内容方向去重

让模型分析：

- 核心问题是否相同。
- 核心观点是否相同。
- 读者价值是否相同。
- 叙事场景是否只是简单替换。
- 文章最终是否会产生相似内容。

重复判断不能仅依赖标题。

## 4.6 建立内容方向分布机制

不能只检查单条选题，还要分析整个赛道的选题组合。

需要统计：

- 主题分布。
- 文章类型分布。
- 创意方向分布。
- 负面冲突型选题比例。
- 方法建议型选题比例。
- 关系话题比例。
- 知识解释型选题比例。
- 历史重复问题簇。

不要设置所有赛道统一的固定比例。

应根据各赛道定位确定合理分布，重点识别单一套路过度集中。

## 4.7 建立 TopicReview

每次选题审核都要记录：

- 选题 ID。
- 审核时间。
- 审核维度和分数。
- 风险项。
- 重复选题。
- 审核理由。
- 最终状态。
- 审核所使用的模型及 Prompt 版本。

# 五、建立文章策划模块 ArticlePlan

文章不能从选题直接跳到全文生成。

必须增加独立的文章策划环节。

## 5.1 策划目标

根据正式选题，自动确定：

- 本文服务的读者。
- 本文要解决的问题。
- 核心观点。
- 文章类型。
- 创作角度。
- 内容组织方式。
- 需要核验的事实。
- 预计篇幅。

## 5.2 ArticlePlan 建议结构

```typescript
interface ArticlePlan {
  id: string;
  topicId: string;
  trackId: number;

  readerProblem: string;
  readerValue: string;

  coreInsight: string;
  articleType: string;
  writingAngle: string;

  structurePlan: Array<{
    section: string;
    purpose: string;
    keyPoints: string[];
  }>;

  factRequirements: Array<{
    claim: string;
    factType: string;
    required: boolean;
  }>;

  estimatedLength?: number;

  contractVersion: string;
  createdAt: Date;
}
```

以上仅为目标结构，实施时可根据现有业务适当调整。

## 5.3 文章结构要求

文章结构必须动态生成。

禁止所有文章都使用：

- 开头提出问题。
- 中间列举三个原因。
- 最后给出三个建议。
- 结尾升华主题。

不同文章类型应有不同的内容组织方式。

例如：

知识解释型文章应重视概念、原理、例子和理解。

经验分享型文章应重视具体经历、过程、反思和可迁移经验。

观点分析型文章应重视观点、论据、分析和合理结论。

故事观察型文章应重视叙事、细节、观察和启发。

这些只是结构参考，不是必须固定套用的模板。

# 六、建立按需事实核验机制

本项目明确不建设传统素材库。

不要求人工持续维护大量文章素材，也不要求每篇文章都先检索资料。

采用：

**AI 自主策划 + 事实需求识别 + 按需核验 + 单篇证据记录。**

## 6.1 事实需求分类

文章策划阶段识别事实需求：

| 类型 | 处理规则 |
|---|---|
| 常识性解释 | 通常可以直接创作 |
| 个人观点 | 可以创作，但不能伪装成事实 |
| 一般方法建议 | 根据专业性决定是否核验 |
| 虚构示例 | 必须明确标注为虚构示例 |
| 真实案例 | 必须有可追溯来源 |
| 统计数据 | 必须核验 |
| 研究结论 | 必须核验 |
| 法律政策 | 必须核验 |
| 医疗健康 | 必须核验 |
| 新闻事件 | 必须核验 |
| 产品版本与技术时效信息 | 必须核验 |

## 6.2 零成本来源方案

不购买付费搜索 API。

第一阶段优先支持：

1. RSS / Atom 公开订阅源。
2. 政府官方网站。
3. 教育机构公开页面。
4. 科研机构公开页面。
5. 产品及技术官方公告。
6. 用户提供的 URL。
7. 用户主动上传的文件。

采用按需抓取，而不是全网爬虫。

来源读取需要遵守网站条款、访问频率和版权要求。

不得将抓取整篇文章作为素材库，也不得直接复制他人文章。

## 6.3 来源核验要求

每条外部事实主张都应有对应来源。

核验时应检查：

- 来源是否真实存在。
- 来源是否能正常访问。
- 来源是否支持当前主张。
- 是否存在断章取义。
- 数据的时间范围是否匹配。
- 是否把相关性错误表达为因果关系。
- 是否把个人观点包装为研究结论。

如果没有找到真实可靠的来源：

- 删除该事实主张。
- 改写为明确的观点或一般性分析。
- 必要时阻止文章进入发布流程。

绝对禁止编造 URL、研究名称、作者、年份和引用内容。

## 6.4 ArticleEvidence 数据模型

建议增加：

```typescript
interface ArticleEvidence {
  id: string;
  articleId: string;

  claim: string;

  sourceTitle?: string;
  sourceUrl?: string;
  sourceType?: string;

  publishedAt?: Date;
  accessedAt?: Date;

  evidenceExcerpt?: string;

  verificationStatus:
    | 'verified'
    | 'pending'
    | 'unverified'
    | 'rejected';

  verificationNote?: string;

  createdAt: Date;
}
```

每篇文章可以没有外部证据，也可以有多条证据。

ArticleEvidence 是文章证据记录，不是传统素材库。

# 七、重构文章生成引擎

## 7.1 生成输入

文章生成服务必须使用以下信息：

- TrackContract。
- 正式选题。
- ArticlePlan。
- 已核验的 ArticleEvidence。
- 全局创作原则。
- 文章类型对应的生成规则。

禁止文章生成服务绕过策划模块，直接从选题标题生成完整文章。

## 7.2 动态 Prompt

建立统一 Prompt Renderer。

职责：

1. 读取全局规则。
2. 读取赛道契约。
3. 读取文章类型。
4. 读取文章策划。
5. 读取核验结果。
6. 组合完整 Prompt。
7. 保存实际使用的 Prompt 内容及版本。

Prompt 应由结构化配置生成，不再散落在多个业务文件中。

## 7.3 文章结构

文章结构应根据 ArticlePlan 动态决定。

不同赛道和文章类型允许采用不同的结构、篇幅和表达方式。

不得强制所有文章使用相同段落数、相同小标题数量或相同开头和结尾。

## 7.4 文章输出

模型输出需要进行结构校验。

至少包括：

- 标题。
- 正文。
- 文章类型。
- 赛道信息。
- 策划关联 ID。
- 使用的配置版本。
- 生成运行 ID。

根据当前项目实际输出协议适配，不要破坏现有微信公众号文章格式。

# 八、建立文章质量审核模块

文章生成不代表文章合格。

必须增加独立的文章审核环节。

## 8.1 审核维度

1. 是否符合选题。
2. 是否符合赛道定位。
3. 是否有实际读者价值。
4. 是否有空洞鸡汤。
5. 是否存在机械化表达。
6. 是否出现内容重复。
7. 是否符合文章形态契约。
8. 是否存在无来源事实。
9. 是否存在虚构案例、数据和引用。
10. 是否存在夸大、误导或标题党。
11. 是否有版权风险。
12. 是否有明显逻辑问题。

## 8.2 审核机制

审核结果应包含：

- 评分。
- 不合格原因。
- 具体问题位置。
- 对应修改建议。
- 事实核验问题。
- 最终审核状态。

审核状态建议：

```text
pending
  |
  v
reviewing
  |
  +----> approved
  |
  +----> needs_revision
  |
  +----> rejected
```

对需要修改的文章，尽可能采用局部定向修改。

不能每次审核失败就要求模型重新生成全文。

文章审核合格后才允许进入待发布流程。

发布仍然保留人工确认，不能因自动审核通过就默认自动发布。

# 十二、技术实现约束

本次改造需要遵守以下要求。

- 后端语言和框架。
- 前端框架。

- 微信公众号接入方式。
- 任务调度方式。

除非有明确的技术原因，不要擅自更换技术栈。

## 12.2 不依赖付费搜索 API

不允许将付费搜索 API 作为系统正常运行的必要条件。

事实核验使用免费公开来源、RSS、官方网页和用户提供资料。

外部来源获取模块必须具有可替换接口。

某一来源不可用时，系统应明确标记无法核验，而不是伪装已经核验。

## 12.3 模型调用

不要将某一家模型的特有能力写死在业务流程中。

应尽可能通过现有模型适配层实现：

- 文本生成。
- 结构化输出。
- 内容审核。
- Embedding（如果可用）。

如果某个模型不支持某项能力，应有明确的降级策略。

## 12.4 错误处理

必须考虑：

- 模型请求超时。
- 模型返回格式错误。
- 结构化输出解析失败。
- 公开来源访问失败。
- 重复任务。
- 数据库写入失败。
- 审核失败。
- 任务中断。
- 重试导致重复入库。

关键写入操作需要考虑事务和幂等性。

## 12.5 代码质量

- 采用清晰的模块职责。
- 尽可能复用现有基础能力。
- 不重复实现同一套业务规则。
- 不通过大量 if/else 维护所有赛道差异。
- 不在多个文件中重复硬编码 Prompt。
- 不为了追求抽象而引入不必要的复杂设计。
- 新增模块必须有对应测试。
- 关键规则必须能够独立测试。

# 十四、建立自动化质量测试集

- 风险说明。

测试以下情况：

1. 高质量新选题。
2. 低价值选题。
3. 情绪冲突型选题。
4. 伪科学选题。
5. 刻板印象选题。
6. 文本重复选题。
7. 语义重复选题。
8. 核心问题重复选题。

## 14.2 文章测试集

覆盖：

- 不同赛道。
- 不同文章类型。
- 不同结构。
- 不同篇幅。
- 有事实核验需求。

- 选题质量。
- 重复率。
- 赛道匹配率。
- 内容多样性。
- 事实核验正确率。

# 十五、最终验收指标

初期建议采用以下工程目标，后续根据真实数据调整。

| 指标 | 计算口径 | 初期目标 |
|---|---|---:|
| 选题赛道匹配率 | 匹配合格数 / 审核总数 | ≥95% |
| 高相似重复率 | 高相似选题数 / 候选总数 | <5% |
| 事实主张可追溯率 | 有有效证据的需核验主张 / 全部需核验主张 | 100% |
| 文章形态符合率 | 符合契约的文章 / 审核文章 | ≥95% |
| 选题质量通过率 | 通过数 / 候选总数 | 观察并逐步优化 |
| 文章一次审核通过率 | 首次通过数 / 审核文章数 | 持续提升 |

注意：

1. 所有指标必须明确统计范围和分母。
2. 数据不足时显示样本不足，不允许伪造指标。
3. 不能通过放宽审核标准来人为提高通过率。
4. 事实核验指标只统计真正需要核验的事实主张。
5. 语义重复率需要说明判定阈值和抽样验证方法。
