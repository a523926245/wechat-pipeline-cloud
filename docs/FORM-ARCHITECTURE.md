# 形态架构方案（后处理 / 段落判据 / 素材查证）

> 状态：2026-11-12 · **设计稿，未实施**。
> 解决三件事：① 两个确定性后处理放哪 ② 段落判据不能硬编码 ③ 素材查证能不能联网。
> 上游：`docs/WRITING-PIPELINE.md`（当前链路）· `docs/TRACK-FORM-RESEARCH.md`（调研结论）。

## 0. 一句话方针

> **赛道是一行配置，不是一段代码。** 代码里永不出现 `if (track === '星座')`；
> 所有差异走「给模型看的自然语言」+「给程序看的结构化 JSON」两套配置，
> 后者有 schema 与边界校验。

现在的 `relax: ['para_shape','para_short']` 就是反例：它是补丁，不是模型。
真实的意图是「这条赛道的段落节奏是切片式」，应该表达成 `rhythm: "sliced"`，
让判据**从语义推导出来**，而不是逐个 code 关掉。

## 1. 数据模型：把 `r:{赛道}` 升级成「赛道机器档案」

`r:{赛道}` 现在只有 `checks` + `angleMode` + `relax`。扩展成：

```jsonc
{
  "checks": ["zodiac_topic", "zodiac_textbook", "zodiac_repeat", "zodiac_dup"],
  "angleMode": "zodiac",

  "form": {
    // ── 段落节奏：决定跑哪些段落判据 ──
    // essay  = 复合长段为主（默认）
    // mixed  = 长场景 + 短判断交替
    // list   = 口语清单，允许一句一段
    // sliced = 一个主体一段（群像）
    "rhythm": "sliced",

    // ── 门禁边界（这是 gate，不是 target）──
    "sections": [3, 4],
    "chars": [1300, 2300],
    "paraMax": 150,

    // ── 群像专用：主体清单（数据，不是代码分支）──
    "subjects": ["白羊","金牛","双子","巨蟹","狮子","处女","天秤","天蝎","射手","摩羯","水瓶","双鱼"],
    "subjectField": "星座",

    // ── 后处理开关：装哪几个步骤 ──
    "postprocess": ["mergeSameSubject"]
  },

  // 最后的逃生门：只在 rhythm 表达不了时用，并在日志里报账
  "relax": []
}
```

### 1.1 `rhythm` 如何替代 `relax`

| rhythm | 长段占比要求 | 一句一段上限 | 额外 |
|---|---|---|---|
| `essay` | ≥1/3 | ≤1/2 | 默认，等价于现在的散文标准 |
| `mixed` | 不检查 | ≤1/2 | 每节至少一段完整场景（在提示词里约束，lint 不判） |
| `list` | 不检查 | 不检查 | — |
| `sliced` | 不检查 | 不检查 | 同一主体不得占两段（`subjectDup`） |

这样 `relax` 从「日常配置」降级为「例外」，正常拓展赛道根本用不到它。

### 1.2 「数值不进自由文本」怎么继续守住

原铁律的动机是：页面写「5 个小节」而门禁按 3-4 拦，自己打自己。
搬到配置里之后，靠**三道闸**守住同一件事：

1. **schema 校验**：`sections` 必须是 `[int, int]` 且 `2 ≤ min ≤ max ≤ 6`
2. **硬边界**（代码里的「宪法」，少量且稳定）：`chars` 必须在 `[1000, 4000]`，
   `paraMax ∈ [80, 300]`，`rhythm` 只能是被枚举的四个值
3. **同源性由渲染保证**：提示词里的数字只能来自 `{{变量}}`，
   而变量值**由这份档案 + 篇幅档注入**——提示词本身存不下数字，就不可能打架

> 校验逻辑放 `services/form/schema.ts`，**API 保存时和读库时共用同一个函数**。
> 这样无论是页面改的、脚本写的、还是直接改库的，坏配置都进不来（读时回落默认 + warn）。

### 1.3 与 `v:{赛道}:length` 的关系（两层，别混）

```
form.chars   = 门禁边界（这篇允许多长）      ← 体检用
v:length     = 本次目标（这一篇想写多长）    ← 提示词用
```

保存篇幅档时校验「target 必须落在 form.chars 内」。这一条就是今天踩过的坑：
星座第一版 target 1400-1650、形态每座 30-70 字，算术上凑不到 1300，稿子必被拦。
**有了校验，这种自相矛盾在保存时就会报错，而不是等真机跑完才发现。**

## 2. 后处理：从「固定链条」改成「步骤表」

### 2.1 现状的问题

`writer.ts` 的 `postProcess` 是硬编码三连：

```ts
sanitizeModelHtml → processEmphasis → reflowParagraphs
```

要加「序号分段」和「同主体合并」，只能往里塞 if——而这两个步骤**只对某些形态有意义**，
塞进去就是所有赛道都跑一遍，典型的牵一发动全身。

### 2.2 目标结构

```
services/postprocess/
  index.ts          runPostProcess(html, ctx) —— 只负责排序与记账
  types.ts          PostProcessStep / PostContext
  steps/
    sanitize.ts       清洗（永远跑，第一）
    emphasis.ts       强调补齐（永远跑）
    split-numbered.ts 序号分段（按需）
    merge-subject.ts  同主体合并（按需）
    reflow.ts         段落重排（永远跑，倒数第二）
```

```ts
export interface PostContext {
  track: string;
  form: FormSpec;        // 来自 r:{赛道}.form（已校验）
}

export interface PostProcessStep {
  name: string;
  /** 只在档案声明时跑；默认 false，避免"新步骤对所有赛道生效" */
  applies: (form: FormSpec) => boolean;
  /** 纯函数：输入输出都是 html，可单测、幂等 */
  run: (html: string, ctx: PostContext) => { html: string; changed: boolean; note?: string };
}
```

`runPostProcess` 的顺序固定为：

```
sanitize → emphasis → [按 form.postprocess 顺序执行步骤] → reflow
```

**新增一种形态的动作 = 新写一个 step 文件 + 在档案里加一个名字，不动 writer、不动别的赛道。**

### 2.3 两个步骤的具体算法

**① `split-numbered`（序号分段）**

适用：`list` / `mixed` 形态（职场自测项、育儿分点）。

```
对每个 <p>：
  找出形如 (段首 | 句末标点后) + 数字 + [.、)] 的位置
  序号 ≥ 2 个 → 按序号切开，序号留在段首
  每个切出来的片段必须以句末标点收尾，否则放弃这次切分（防误切散文）
  幂等：无序号或只有 1 个 → 原样返回
```

**② `merge-subject`（同主体合并）**

适用：`sliced` 形态，且档案里有 `subjects`。

```
相邻两段，各自只提到 subjects 里的同一个主体（没有第二个主体）→ 合并
合并后字数 > form.paraMax → 放弃合并（不制造巨段）
幂等：没有可合并的相邻对 → 原样返回
```

两条都是纯函数，都能在 `smoke:lint` 里用固定 HTML 断言，不依赖模型。

## 3. 素材查证：不是「不能联网」，是「没接检索」

先把事实说清：

- **网络不是限制**：服务端是 Node，想发 HTTP 就发。
- **模型也不是不会搜**：取决于厂商是否开放联网/工具调用。当前 `llm.ts` 只发普通
  chat completion，不传任何 tools —— 所以现在**模型看不到任何外部信息**。
- 于是「查不到出处就不写」这条，模型的实际解法是**不引用**。结果不是「引用错了」，
  而是「整篇文章没有一处可核实的支撑」，教育/科技这种事实密集的赛道吃亏最大。

### 3.1 三个选项的取舍

| 方案 | 做法 | 代价 | 适合 |
|---|---|---|---|
| A 现状 | 只禁无出处引用 | 零成本，但文章没有支撑 | 星座 / 激励（本来不需要外部事实） |
| B 模型自带联网 | 传 tools 让厂商侧搜 | 便宜，但**我们不知道它读了什么**，无法审计；引用质量不可控 | 不建议做主路径 |
| C 服务端检索（RAG-lite） | 写前检索 3-5 条，注入「可引用素材」 | 每条一次网络调用 + 人工抽检 | **教育 / 科技** |
| D 事后核对 | 写完抽出所有引用，逐条回查 | 多一轮调用 | 只在教育开启 |

**推荐 C 为主、D 为教育赛道的补充；A 继续用于不需要事实的赛道。**

### 3.2 接口设计（关键：可插拔，不侵入 writer）

```
services/research/
  index.ts            gatherFacts(query, opts) → FactPacket | null
  types.ts            FactPacket / FactItem / ResearchProvider
  providers/
    http-search.ts    外部搜索 API
    none.ts           关闭（返回 null）
```

```ts
export interface FactItem {
  title: string;
  publisher: string;   // 发布方
  date: string;        // 有就写，没有就空
  url: string;
  snippet: string;     // 摘要，控制在 120 字内
}

export interface FactPacket {
  query: string;
  items: FactItem[];
  fetchedAt: string;
  provider: string;
}
```

写稿侧只加两行：

```ts
const facts = needsResearch(form) ? await gatherFacts(angle, track) : null;
// 插在 user prompt 的规范区之后、tail 之前：【可引用素材】
```

`FactPacket` **落库到 Article**（新字段 `factPacket`），这样：

- 推送前能审计「这篇文章引用的到底是什么」
- 事后能回查「模型有没有引用素材之外的东西」
- 出问题能定位到「哪次检索、哪个来源」

### 3.3 什么时候触发

由档案声明，不由赛道名判断：

```jsonc
"research": {
  "mode": "required" | "optional" | "off",
  "maxItems": 5
}
```

- 教育：`required`（涉及政策必须给来源）
- 科技：`optional`（有就引用，没有就用生活比喻讲）
- 星座 / 育儿 / 激励 / 职场：`off`

`factPacket` 为空而 `mode=required` 时，`generateDraft` 的 note 里要写明
「本次检索无结果，引用已降级」，而不是静默按 A 方案处理。

## 4. 落地顺序（三个独立小步，每步都能单独回滚）

| 步 | 内容 | 影响面 | 验收 |
|---|---|---|---|
| **P1** | `form` 档案 + schema 校验；`constants` 降级为默认值；`lint` 改读档案；`relax` 退居例外 | 只动 lint 与读配置，**产出不变** | `smoke:lint` 全过 + 同一批旧稿体检结果逐项一致 |
| **P2** | 后处理步骤表 + `split-numbered` + `merge-subject` | 只动 postProcess，按 `form.postprocess` 生效 | 固定 HTML 单测 + 真机各赛道 1 篇对比段数 |
| **P3** | `research` 适配器（默认 `none`，先只开教育） | 只加一个可选步骤，不接就是 null | 教育 1 篇：素材进 prompt、`factPacket` 落库、引用可核对 |

P1 必须先行：P2 的开关和 P3 的触发条件都读 `form`。

## 5. 「不牵一发动全身」对照表

| 想做的事 | 改哪里 | 会不会影响别的赛道 |
|---|---|---|
| 新增一条赛道 | 赛道管理 + 文风配置页填五项 | 不改代码，默认走 `essay` 档案 |
| 某赛道改成清单体 | `r:{赛道}.form.rhythm = "list"` + `postprocess:["splitNumbered"]` | 不影响 |
| 某赛道段落判据不同 | 改 `form` 的 `sections/chars/paraMax` | 不影响 |
| 新增一种后处理 | 加一个 step 文件 + 在档案里写名字 | 不写就不跑 |
| 换个检索引擎 | 加一个 provider 文件 | writer 不动 |
| 改门禁绝对下限 | `form/schema.ts` 的硬边界 | 全局生效（这是宪法） |

## 6. 需要你拍板的三件事

1. **`form` 放哪**：塞进 `r:{赛道}`（一个机器档案，少一个 key），还是单独开 `g:{赛道}`？
   —— 我倾向 `r:`，因为 `r:` 的语义已经是「不直接进 prompt 的机器规则」。
2. **绝对下限要不要守 1300**：允许某条赛道把 `chars` 下限降到 1000 吗？
   —— 我建议不允许（1000 字以下在公众号里基本撑不起一篇）。
3. **检索要不要做 P3**：如果做，需要你提供一个可用的搜索 API（或确认用哪家）。
   —— 不做也行，教育稿就继续「有出处才引用、没有就不写」，只是文章会偏薄。

## 7. 实测：提示词到底能做到哪一步（2026-11-12）

先把「能不能只靠提示词」这件事量出来，再决定要不要写代码。

### 7.1 实验设置

- 模型：Agnes 3.0 Flash（写入角色绑定的那个），参数走模型默认
- 走完整生产链路（含定向修补 ≤2 轮）
- 判据：
  - **多序号段** = 一个 `<p>` 里有 ≥2 个「1. 2.」这样的序号
  - **续段** = 段落以「因为 / 为什么」开头（说明它本该并进上一条）
  - **同座多段** = 同一星座名出现在 ≥2 个段落

### 7.2 结果

| 轮次 | 改动 | 样本 | 坏段情况 | 结论 |
|---|---|---|---|---|
| 基线 | 无清单规则 | 职场 1 篇 | 7 条自测项只落成 5 段 | 坏 |
| 收紧① | `s:` 加「解释写在同一段」 | 职场 3 篇 | 2 篇各剩 1 处坏段，1 篇干净 | **改善，未清零** |
| 收紧① | 同上 | 教育 2 篇 | 2 篇全干净 | 教育没有编号条目，不受影响 |

| 轮次 | 星座编号规则 | 样本 | 星座数 | 同座多段 |
|---|---|---|---|---|
| 基线 | 「禁止给同一个星座写两段」 | 1 篇 | 8 | 5 个星座各 2 段 |
| 收紧① | +「每个星座名只出现一次」+「除星座段外最多 4 段」 | 3 篇 | 9 / 2 / 11 | 0 / 0 / 3 个 |
| 收紧② | 删掉冲突的「单星座深挖」骨架卡 | 3 篇 | 11 / 10 / 6 | 3 / 0 / 1（双鱼×6） |
| 收紧③ | 改成「恰好 10 个」 | 4 篇 | 9 / 10 / 0 / 8 | 9 / 4 / 0 / 8 个 |
| 收紧④ | 十二座写满 + 小标题「类别 + 数量」 | 4 篇 | **12 / 12 / 12 / 11** | 3 / 2 / 11 / 2 个 |
| 收紧⑤ | + 每段以「星座名：」开头 + 固定 17-19 段 | 4 篇 | 11 / 12 / 11 / 12 | 10 / **12** / 5 / 10 个（更糟，已回退） |

**星座合计 15 篇：同座多段为 0 的只有 2 篇。**

### 7.3 结论：把「星座的问题」拆成三件事

| 子问题 | 能靠提示词吗 | 证据 |
|---|---|---|
| **覆盖率**：写几个星座 | **能** | 「9-11 个」落区间 2/6；改「恰好 12 个」后 4/4 命中 |
| **篇幅 / 段数**：写多长 | **能** | 段数从 16-30 收敛到 17-26 |
| **唯一性**：每个只写一段 | **不能** | 20 篇里只有 2 篇干净；继续加提示词反而更糟 |

为什么唯一性管不住：它是**跨 20 多段的全局约束**，模型写到第 15 段时不会回头数前面写了谁。
而「写几个」「写多长」是**可数的局部指标**，模型数得清——这跟「段数比字数好使」是同一条经验。

两个副产物也值得记：

- 小标题写「那三个 / 那几个」时，正文会跟着**通篇不点名星座**（实测一篇 0 个星座名）；
  改成「火象三座：…」这种「类别 + 数量」后，覆盖率立刻稳。
- 给段落加「星座名：」开头**反而更糟**：等于给了模型「再起一段」的许可。已回退。

### 7.4 因此建议的最小代码量

只加**一个**通用后处理步骤 `mergeSameSubject`（相邻段只提到同一主体则合并），
主体清单来自配置 `form.subjects`——代码里没有赛道名，任何赛道都能开或不开。
清单条目那条**先不加**，靠提示词 + 人工扫一眼。

## 8. 探测：Agnes 到底能不能联网

用模型自己绑定的 key 直接打了三次 `chat/completions`（不经过产线）：

| 探针 | 请求 | 结果 |
|---|---|---|
| A | 标准 `tools`（声明一个 `web_search` function）+ `tool_choice:auto` | **HTTP 200，返回 `tool_calls`** → 支持 function calling |
| B | 厂商内置工具 `tools:[{type:"web_search"}]` | **HTTP 400** → 不支持厂商侧联网插件 |
| C | 不带 `tools`（基线） | 200，模型自述「我目前没有联网搜索或实时查询的能力」 |

**结论：模型不会自己搜，但可以被我们「喂」检索结果。**

这直接决定了方案：

- ❌ 不能指望「让模型自己上网」——它没有这个能力
- ✅ 正确做法：**服务端检索 → 结果注入 prompt**（或走 function calling 让模型发起，
  但注入更简单、更可审计）
- 走 function calling 也行（探针 A 证明支持），但多一轮调用，且我们仍然要把结果存下来

所以 `docs/FORM-ARCHITECTURE.md` 第 3 节的 C 方案（服务端检索 + `FactPacket` 落库）
是唯一可行路线，只是需要你提供一个搜索 API 的 key。

### 8.1 关于「所有文章都要有据可依」

需要区分两种「据」：

| 类型 | 赛道 | 「据」是什么 | 怎么保证 |
|---|---|---|---|
| 事实型 | 教育、科技 | 外部来源，URL 可核 | 检索 + 落库 `factPacket` + 推送前审计 |
| 经验型 | 星座、育儿、激励、职场 | 具体场景、具体行为、读者能验证的细节 | 提示词 + lint（禁学术引用、要求具体物件） |

强行给经验型赛道要求 URL，会把它写成科普文——而「不塞学术引用」正是星座赛道的硬禁忌。
