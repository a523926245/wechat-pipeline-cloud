# 微信公众号自动创作系统重构：最终执行总纲

**文档版本**：V1.0（2026-11-12 用户定稿）| **效力**：本文件是重构执行的**最高级约束**，`docs/restructure/` 其余文档与本文件冲突时以本文件为准。

---

## 一、项目目标

在保留现有技术栈、业务功能、历史数据和 article/comic 双产线的前提下，对微信公众号自动创作系统进行渐进式重构。

本次重构的核心目标不是重写系统，而是建立一套可靠的 AI 内容生产体系：

1. 统一文章形态契约和 Prompt 规则。
2. 建立选题候选、审核、去重和正式入库机制。
3. 建立文章计划、事实证据、质量审核和修订闭环。
4. 建立 Prompt 版本管理和单次模型调用追溯。
5. 重构 UI/UX，使系统成为真正的 AI 内容编辑部工作台。
6. 建立可靠的数据库迁移、备份、测试和回滚机制。

## 二、不可违反的约束

1. 不推倒重建，不随意更换现有技术栈。
2. 不删除或破坏现有功能和历史数据。
3. 保留 article/comic 双产线，comic 业务流程暂不重构。
4. 微信公众号群发永远人工操作。
5. AUTO_PUBLISH=false 是不可修改的安全红线。
6. 系统只负责向微信公众号草稿箱推送，不自动群发。
7. 所有数据库写操作、迁移演练和测试必须使用隔离数据库。
8. 禁止对真实生产数据库进行试验、清理或未经批准的迁移。
9. 不接入需要付费的搜索 API。
10. 不允许使用假数据伪装尚未实现的业务能力。
11. 不允许把 AI 推测结果伪装成已验证事实。
12. 任何破坏性操作必须先说明影响范围、备份方案和恢复方案。

## 三、核心架构决策

### 1. 内容规则

建立统一规则层级：

- **L0**：系统安全红线和不可违反的全局原则。
- **L1**：TrackContract，管理结构、篇幅、段落、主体数量和质量规则。
- **ArticlePlan**：管理单篇文章的读者问题、核心观点、结构和事实要求。
- **L2**：StylePrompt，管理文风、语气、句式和变体。

所有 Prompt 由统一 Renderer 按任务类型组装。所有生成内容由程序门禁验收，Prompt 文本不能覆盖更高层级的结构约束。

### 2. 选题模型

采用 **Angle.status + used + TopicReview**。不建立独立 TopicCandidate 表。

- 审核状态：candidate / needs_revision / approved / rejected。
- used 单独表示是否已被生产任务消费。
- 生成选题先进入候选状态，不允许直接进入正式题库。
- 只有审核通过的选题才能进入生产计划。
- 语义去重失败时，候选可以保留，但不得自动升格。

### 3. 文章生产

引入 ArticlePlan、ArticleEvidence、ArticleReview。

- 文章审核状态与 Article 生命周期、发布状态分开。
- 支持审核、修改、复审、人工覆盖和完整历史记录。
- 无法验证的事实必须明确标记，不得虚构来源。

### 4. 追溯

引入 PromptVersion 和 GenerationRun。

- 区分 Prompt 模板版本、模板 hash、实际渲染 Prompt hash 和单次模型调用。
- 记录必要的模型、任务、耗时、token、输入输出摘要和错误信息。
- 敏感信息脱敏，执行 30 天保留策略前先确认实际合规和业务需求。
- 历史文章没有真实追溯记录时标记为 legacy，不得伪造。

### 5. UI/UX

以 **AI Editorial Studio** 为整体设计方向。

- 优先整理现有设计令牌和 UI-GUIDE，不推倒重建组件体系。
- 先完成设计系统、导航和壳层，再按照后端 API 能力滚动重构业务页面。
- 所有业务状态必须来自真实 API。

## 四、实施顺序

- 阶段 0：设计系统、UI 壳层和导航。
- 阶段 1：数据库迁移、形态契约、配置迁移、Renderer 和 PromptVersion。
- 阶段 2：选题状态机、审核、去重和选题中心。
- 阶段 3：ArticlePlan、ArticleEvidence 和事实核验。
- 阶段 4：文章生成、审核、修订、GenerationRun 和发布门禁。
- 阶段 5：质量中心、AI 运行中心、完整测试和系统验收。

阶段 0 与阶段 1 可以并行，但业务 UI 不得早于对应后端 API 和状态定义上线。阶段 1 内部拆分 migration baseline、契约配置和 Renderer 三个里程碑。

## 五、工程执行要求

每个阶段必须：

1. 先检查现有代码和数据，不凭猜测修改。
2. 提交实施计划和文件影响清单。
3. 明确 API、数据库和前端改动范围。
4. 在隔离数据库中验证所有数据库变更。
5. 建立单元测试和集成测试。
6. 执行 TypeScript 检查、构建、smoke test。
7. 验证旧功能和双产线。
8. 提供可回滚或向前修复方案。
9. 更新技术文档和 CHANGELOG。
10. 输出真实测试结果和未完成事项。

禁止一次性修改大量无关模块。

## 六、工作方式

本项目采用**分阶段授权**。在我明确同意开始某个阶段之前，不得实施该阶段的代码或数据库修改。

每个阶段开始前，先提交：本阶段目标 / 详细任务清单 / 受影响文件 / 数据库变更 / API 变更 / UI 变更 / 测试计划 / 风险和回滚方案。

阶段结束后，提交：实际修改文件 / 完成情况 / 测试结果 / 数据库变更结果 / 与原设计的差异 / 遗留问题 / 下一阶段建议。

如果实施中发现原设计不合理，先说明问题、影响和替代方案，不得擅自扩大修改范围。

**最终原则：优先保证内容质量、数据安全和系统可维护性，其次才是开发速度和功能数量。**

## 七、五项核心验收指标（2026-11-12 追加，与正文同等效力）

> 本系统最终不能只用「能不能成功生成文章」来衡量。整个重构项目的验收依据是以下五个指标。
> **最终目标不是让系统每天生产更多文章，而是让系统持续生产符合公众号定位、正向、有价值、不重复、质量稳定的文章，同时显著减少人工筛选和修改工作。**

| 指标 | 衡量目标 | 分子 | 分母 | 统计周期 | 数据来源 |
|---|---|---|---|---|---|
| ① 选题审核通过率 | 选题生成质量 | 期内转为 approved 的候选数（含改后通过） | 期内进入审核的候选总数（含被拒） | 周/月滚动，按赛道切片 | Angle.status 流转 + TopicReview |
| ② 选题重复率 | 题库是否真正减少重复 | 期内被判定重复（文本/语义/内容方向任一层）而拒收或标重的候选数 | 期内候选总数 | 周/月滚动 | TopicReview.dupHits + 守门日志 |
| ③ 文章一次审核通过率 | 文章生成质量 | 首轮 ArticleReview.verdict=approved 的文章数 | 期内完成首轮审核的文章数 | 周/月，按赛道/形态切片 | ArticleReview(round=1) |
| ④ 事实核验覆盖率 | 事实风险是否可控 | 已处理的需核验主张数（verified 或明确 unverified/rejected） | 全部需核验主张数（factRequirements.required=true） | 周/月滚动 | ArticlePlan.factRequirements + ArticleEvidence |
| ⑤ 人工修改工作量 | AI 是否真正减少人工 | 每篇人工编辑动作加权（人工保存次数、人工改动段落数、AI 改写应用数、人工覆盖审核次数） | 期内文章篇数 | 周/月滚动 | 编辑页行为埋点（阶段 4/5 引入）+ ArticleReview 人工覆盖记录 |

**口径纪律**：

1. 每个指标必须标注分母、统计周期与数据来源，禁止展示无口径的百分比。
2. **样本不足时显示「样本不足」**（建议阈值：分母 < 10 不出百分比，只出原始计数），不得随意展示百分比。
3. 不得通过放宽审核标准提高通过率；放宽本身要作为变更记录在案。
4. 指标⑤依赖编辑页埋点，未接入前显示「未接入」，不得估算。
5. 基线采集自阶段 5 起，每阶段验收报告附带本期五项指标快照。
