### 14.2 Fingerprint 实现审计结论（只读代码核对，未连库、未执行 fp）

**计算口径**
- **18 张表**：`BUSINESS_TABLES` 17 张 + `_prisma_migrations`（`smoke-isolated.ts:66-80`）。
- 每表两条语句：`SELECT COUNT(*) AS n FROM \`t\`` 与 `CHECKSUM TABLE \`t\``（`:320-321`）；拼成 `t:count#checksum` 后取 SHA-256。
- **固定数组顺序**逐项 push（`:323-329`），不依赖 SQL `ORDER BY`、不迭代 Map/Object 键序 → **不存在排序不确定性**。
- 数据范围只有「行数」与「整表校验和」，不读取任何行/列内容。

**dev.db 独立比较**
- dev.db **不在**业务库指纹内，是**另一条独立判据**：`fingerprintDevDbFile()`（`:296-303`）记录 `sha256 + size + mtimeMs` 三项。
- MISMATCH 触发条件是「业务库指纹变化 **或** dev.db 三项（含 mtime）任一不同」（`:622`）。
- **本轮 dev.db 结论（谨慎措辞）**：`sha256=fea0f123…` 与 S2 记录一致、`mtime` 停在 2026-11-12 13:20、`prisma/` 目录近 2 小时无改动 → **目前未发现 dev.db 发生变化的证据**；但无法据此**完全排除**首次执行期间曾出现过短暂变化（例如被写后又被还原，mtime 亦可能被工具复位），故只表述为"未发现变化证据"，不表述为"确定未变"。

**取证损失（如实登记）**
- MISMATCH 分支本会打印 `REAL-FP business-db before=… after=…` 两个哈希（`:624`），但当时输出经 `grep` 过滤，**这两行被过滤丢失**，未能留下"哪张表、前后差多少"的直接证据。

**两项无法排除的可能性**
1. **`CHECKSUM TABLE` 瞬时波动**：MySQL 文档明确该语句不保证跨版本对同一表返回同值；同版本对未改动表通常稳定，但 InnoDB 整表扫描计算理论上受页布局/表重建影响。
2. **真实写入后被清理**：若写入与清理都落在第一次 run 的前后两次取指纹之间，第一遍报 MISMATCH；清理在第二遍开始前完成，则第二遍前后一致报 MATCH。

**关键限定**：**第二次 MATCH 不能证明第一次执行期间没有发生过写入**——MATCH 只证明第二遍执行期间状态稳定。`CHECKSUM` 波动与"写入后清理"**两种成因均无法从代码排除**。

**fp 命令的两项已知限制**（本次审计发现，尚未执行）
- **无服务端身份核验**：`printFingerprint()` 只从连接串解析库名打印 `database=`，不执行 `SELECT DATABASE()` / `CURRENT_USER()` / `VERSION()`。
- **存在 `DATABASE_URL` 覆盖风险**：`loadBaseUrl()` 让 `process.env.DATABASE_URL` **优先于** `server/.env`；若 shell 残留了指向隔离库的连接串，fp 会连错库（代码里有 `[fp] WARN` 兜底，但那是 URL 推断而非服务端确认）。故将来执行前必须 `unset DATABASE_URL` 并核对输出的 `database=wechat_pipeline`。
- 另：fp 只输出**当前**单次指纹，只能判定"是否留下持久改动"，**不能判定第一次 MISMATCH 的成因**。
