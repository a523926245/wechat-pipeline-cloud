**日期**：2026-11-12 | **来源**：用户对《阶段 0 实施计划（v1）》的审查意见 | **效力**：阶段 0 实施计划必须按本指令修订后执行；本指令与 v1 计划冲突时以本指令为准
**接收方**：AI 编程助手（修订计划 → 列出执行前检查结果 → 等待最终开工授权）

## 〇、总体方针（本次审查最重要的一点）

阶段 0 不应只是「把现有 UI 整理得更统一」，而应**让系统开始具备一个真正成熟的内容生产后台的产品形态**。
**AI Editorial Studio（AI 内容编辑部工作台）是阶段 0 的设计主线**——所有视觉、布局、组件、原型决策都围绕这条主线收敛。
阶段 0 完成后，应能明显感受到：这是一个成熟的 AI 内容编辑部，而不是一个简单拼装起来的管理后台。

## 一、必须调整的 6 处

### 1. T4 三态组件：分批接入，禁止全站机械替换
- 全站 13 页一次性机械替换风险高：各页业务状态不同；成熟状态逻辑易被替换退化；出问题难区分组件问题还是接入问题。
- **两步走**：①先建立 6 个基础组件，定义统一 Props、状态语义、使用规范与视觉规范；②分批接入——第一批 Dashboard、选题页面（验证组件设计）→ 第二批 文章、文风、模型等（按实际需要）→ 第三批 剩余页面（检查后统一）。
- **不要求为覆盖率强制替换**。
- AppTaskProgress 无真实任务 API：只允许定义组件结构与状态展示规范，**禁止为展示它而制造虚构任务**。

### 2. T1 令牌合并：建立完整视觉语义体系，不是 CSS 变量整理
- 必须覆盖的语义类别：品牌色（主/辅/强调）、背景（页面/卡片/悬浮层/输入框）、文字（主/次级/辅助/禁用）、边框（默认/悬浮/聚焦/分割线）、状态（成功/警告/错误/信息）、交互（Hover/Active/Focus/Disabled）、布局（圆角/间距/阴影/层级）。
- **品牌主色 #0a7c47 不变**。
- 避免「所有状态都用品牌绿」造成视觉层级混乱——状态色必须语义化。
- 暗色模式不能只检查 CSS 变量有值，必须检查**实际页面渲染效果**：表格与弹窗、表单禁用态、编辑器、Element Plus 覆盖样式、错误/警告/成功提示。

### 3. T2/T3 导航：明确页面职责，选题中心一级入口
- 最终导航定稿：
  - 工作台
  - 内容生产：选题中心 / 创作计划 / 文章工作台
  - 内容策略：赛道管理 / 文风配置 / 标题前缀
  - 运营与系统：调度管理 / 公众号账号 / 模型配置 / 用户管理
- `/angles` 不是简单换 URL，必须验证：
  1. 无赛道 ID 时能正常展示；
  2. 赛道切换正常；
  3. 切换后数据确实来自对应赛道；
  4. 浏览器刷新保留合理页面状态；
  5. 原 `/tracks/:id/angles` 深链继续正常。
- 若 TrackAnglesView 强依赖路由参数，**先做兼容层**，不许简单复制路由配置。

### 4. T5 AI 操作披露：统一五项 + AI/人工视觉区分
- 每个 AI 操作统一披露五项：
  | 项目 | 示例 |
  |---|---|
  | 输入 | 当前赛道、选题、参考素材 |
  | 产出 | 生成 10 个候选选题 |
  | 数据影响 | 仅生成候选，不进入正式题库 |
  | 可撤销性 | 可删除候选或恢复之前版本 |
  | 资源消耗 | 模型、调用次数及可获得的消耗信息 |
- **AI 生成 / AI 修改 / AI 审核 / 人工确认，必须有明确视觉区分**（徽标/标记体系），否则功能变多后用户无法判断内容是 AI 产出还是已人工确认。

### 5. T6 原型：静态 HTML 可以，但必须表达完整操作流程
- 三个原型：①选题审核中心 ②文章编辑与审核工作区 ③形态契约配置页。
- 原型不是画一个页面，要表达完整操作流程。选题审核中心至少体现：候选状态、赛道筛选、重复风险、质量评分、审核原因、通过/修改/拒绝、批量审核、审核历史。
- 明确标注的模拟数据可以使用，但**必须标注为原型数据，不得接入生产业务页面**。

### 6. T7 走查：增加视觉验收标准 + 改造前后截图
- 验收维度：页面层级（标题/描述/操作区清晰）、视觉统一（按钮/表格/卡片/弹窗一致）、信息密度（无大片无意义留白）、操作效率（高频操作不反复跳转）、状态反馈（加载/空/错误清楚）、暗色模式（文字/边框/背景对比度足够）、响应式（1180/768 无严重布局破坏）。
- 截图必须保留：改造前 / 改造后 / 亮色 / 暗色 / 1180px / 768px，用于判断改造是否真正改善 UI。

## 二、安全前置（必须优先处理）：冒烟测试的数据库安全
v1 计划「smoke 按既有脚本惯例运行」的表述不安全。项目发生过两次数据事故，不能仅凭脚本名称或说明认定不影响生产数据。
执行阶段 0 前必须检查并报告：
1. smoke:lint 实际执行什么脚本；2. smoke:style 同；3. smoke:angles 同；
4. 各脚本读取哪个数据库连接地址；5. 是否存在 create/update/delete；
6. 数据回收逻辑是否可能误删正式数据；7. 测试失败时是否可能留下残余数据。

**只有确认测试使用隔离数据库，才允许执行可能产生数据库写入的冒烟测试。无法确认就只运行静态检查和前端构建，不为完成测试清单冒险。**
另增要求：测试开始前打印实际数据库环境标识；对非隔离环境的写操作设置阻断。

## 四、补充要求：阶段 0 视觉设计基准
必须建立**一套可持续复用的后台视觉语言**，不是单纯完成组件封装。具体包括：
页面布局规范、页面标题与说明规范、卡片与内容容器规范、表格和列表规范、按钮层级规范、弹窗与抽屉规范、表单布局规范、状态反馈规范、亮色与暗色主题规范、页面间距与信息密度规范。
**避免 Element Plus 默认风格直接铺满整个系统**：EP 继续作基础组件库，但最终视觉呈现由自有设计系统控制。

## 五、执行顺序（定稿）
1. 安全检查：确认冒烟测试与数据库隔离（含环境标识打印 + 非隔离写阻断）。
2. T1：设计令牌盘点与合并（视觉语义体系）。
3. T2/T3：壳层、导航、选题中心入口（含 /angles 兼容层验证清单）。
4. T4：六个组件建立，分批接入（第一批 Dashboard+选题）。
5. T5：完善 UI-GUIDE 与 AI 操作披露规范（含 AI/人工视觉区分）。
6. T6：三个静态 HTML 原型（流程完整、原型数据标注）。
7. T7：真实浏览器走查、截图（改造前后×亮暗×1180/768）和问题修复。
8. T8：测试、文档、阶段报告和回滚检查。
